# Data

SignalFlow ships everything it needs; no dataset download is required to run.

## 1. Sensor-count feed (junction model)

* `data/sample_traffic.csv` — 43 200 rows (60 min × 12 movements), 4 315 vehicles.
* Columns: `t_seconds, minute, second, approach, movement, vehicles_count`.
* Regenerate: `python3 data/generate_sample.py` (synthetic, seeded, Poisson around
  the default peak rates with a rush-hour ramp).

**Why synthetic?** The challenge brief references a *"sample open traffic-sensor
dataset … provided at the briefing"*. We verified that no such file is publicly
downloadable (the `/downloads/...` URLs return only the app shell), so we ship a
synthetic stand-in with the **same shape**. When the real dataset is released,
point `arrival_csv` at it — no code change:

```jsonc
// POST /api/simulate
{ "arrival_source": "csv", "arrival_csv": "data/real_briefing_counts.csv",
  "detector_dropout": 0.05 }
```

The loader accepts either `t_seconds` or `minute`+`second`, tolerates extra
columns, tiles a feed shorter than the horizon, and truncates a longer one.

## 1b. Adapter for third-party sensor feeds

Real detector exports rarely match our columns. `signalflow/feed_adapter.py` (CLI:
`tools/adapt_feed.py`) auto-detects common shapes and normalises them to our
canonical feed `t_seconds,approach,movement,vehicles_count`:

```bash
python3 tools/adapt_feed.py --make-example data/example_sensor_generic.csv
python3 tools/adapt_feed.py data/example_sensor_generic.csv --out data/example_sensor_adapted.csv
python3 -m signalflow.feed_adapter IN.csv --json          # same tool, module form
```

Recognised inputs: our **canonical** shape, and **generic sensor exports** such as
`timestamp, device_id|location|zone, traffic_count [, avg_speed, status]` (the shape
of the public Kaggle "Smart City Traffic Flow Prediction" sample).

Reconstruction rules (deterministic):

| Missing piece | Rule |
|---|---|
| `approach` | explicit if present; otherwise the location/device keys are **sorted** and assigned N, E, S, W, N, ... — override with `--mapping map.json` |
| `movement` | explicit if present; otherwise split by `--split L,T,R` (default 0.15, 0.70, 0.15) using **largest remainder**, so totals are preserved exactly |
| time | ISO or `HH:MM` timestamps parsed into seconds from the first sample; `--per-second` spreads a coarse count evenly across its interval |

Output goes straight into the app with no code change:

```json
{ "arrival_source": "csv", "arrival_csv": "data/example_sensor_adapted.csv", "duration_min": 10 }
```

Shipped examples (both **synthetic**, generated by the tool): `data/example_sensor_generic.csv`
(4 zones, 30 min, minute resolution) and `data/example_sensor_adapted.csv` (its canonical
form). Adapter tests live in `tests/test_feed_adapter.py`. The briefing's real dataset can
be dropped in the same way once it is available.

## 2. Street networks (district model)

Source: **OpenStreetMap** via Overpass. Pipeline:

```
tools/fetch_osm.py      # query Overpass -> data/osm/<region>.json (raw)
tools/build_regions.py  # raw -> data/regions/<region>.json (graph)
tools/verify_regions.py # sanity-check the graphs
```

Query classes: `motorway, trunk, primary, secondary, tertiary, unclassified,
residential, living_street, *_link`, plus `node[highway=traffic_signals]`.

**Builder rules**
* A graph **node** is a coordinate shared by ≥2 ways, a way endpoint, or a node
  with a traffic signal within 15 m.
* A **link** is a run between two graph nodes along a way; `length_m` is the sum of
  haversine segments. Reverse links are generated for non-`oneway` streets.
* `lanes` from the tag (defaults by class); `speed_kph` from `maxspeed` (defaults by
  class); `oneway` from the tag / roundabout / motorway.
* `deg` = number of distinct neighbours; a node is `signal` if flagged or `deg ≥ 4`.

**Note on mirrors:** `overpass.osm.ch` is reachable but is a **Switzerland-only**
mirror and returned 0 elements for Munich; the fetch uses a reachable global mirror
with retry/backoff. `overpass-api.de` returned 406 from this environment.

City regions use an **arterial scope** (motorway…tertiary + links, no residential)
to keep large inner-city extracts tractable and realistic for signal coordination.
All six appear automatically in the dashboard's region selector via `/api/regions`;
new cities are added as one line in `tools/fetch_osm.py` and re-running the
fetch/build pipeline.

Graph JSON schema (`data/regions/<id>.json`):
```json
{ "region": "expo_riem", "name": "Messe Muenchen / ICM Riem",
  "bbox": [48.128, 11.683, 48.144, 11.708],
  "nodes": [{"id":int,"lat":f,"lon":f,"deg":int,"signal":bool}],
  "links": [{"id":int,"from":int,"to":int,"length_m":f,"lanes":int,
             "speed_kph":int,"oneway":bool,"name":str|null,"hw":str}],
  "stats": {"nodes":int,"links":int,"signals":int,"junctions":int} }
```
